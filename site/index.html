How it works

  

    
1
One image
A CUDA 12.1 runtime image with torch from the cu121 wheel index. train.py uses the GPU when it is there and falls back to CPU when it is not.

    
2
Two ways to schedule
A Kubernetes Deployment asking for nvidia.com/gpu: 1 per pod, a Kubeflow PyTorchJob for multi-node training, or an sbatch script on Slurm.

    
3
One pipeline
The Jenkinsfile builds and pushes the image on main, applies the manifest, waits for the rollout and rolls back on timeout.

  






  
Run it yourself

  
The tests run on CPU, no GPU needed.

  

    


pip install -r requirements-dev.txt
pytest -v

kubectl create namespace gpu-workloads
kubectl apply -f pytorch-gpu-deployment.yaml

    

    


kubectl apply -f pytorch-distributed-job.yaml

sbatch pytorch_job.sh
squeue -u $USER

      
The device plugin or GPU Operator must be installed first. The PyTorchJob needs the Kubeflow Training Operator.

    

  






  
What this does not do
    
    
  • The training job is a small demo model on random data. It exists to exercise the deployment, not to train anything useful.
    • 
    
  • This page has no GPU and runs no PyTorch. The planner and the Slurm check are page-side arithmetic.
    • 
    
  • The image and registry names in the manifests and Jenkinsfile are placeholders for your own.
    • 
    
  • On failure the Jenkinsfile calls an OpenAI-based triage step from the shared library.
